# puerto-rico-web — Web/API Layer + Human Actor Adapter

See [docs/architecture.md](../docs/architecture.md) for how this module fits
into the whole system.

## Intent

The only part of the system that talks to browsers. Translates HTTP
requests into Lobby actions, and moves arriving over HTTP into answers for
the Human Actor Adapter; pushes game events back out to connected clients
— both seated players and spectators — over Server-Sent Events.

This module also owns the **Human Actor Adapter** (`HumanActor`): the
piece that turns "wait for a move to arrive over the network" into an
answer to the Decision contract defined by `puerto-rico-session`, so a
human player is just another actor from the Session's point of view. It
lives here rather than as a standalone module because it's inherently a
web-connection concern — it has no existence independent of a browser
session.

## Contracts

Implements the endpoints defined by `puerto-rico-contract`'s OpenAPI spec —
`LobbyController`, `GameController`, and `AiController` each `implement`
their generated interface directly, so the spec and the implementation
cannot drift without a compile error:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/games` | Create a table |
| `GET` | `/api/games` | List tables |
| `GET` | `/api/games/{id}` | One table's summary |
| `POST` | `/api/games/{id}/seats` | Seat a human or AI engine |
| `POST` | `/api/games/{id}/start` | Start the game |
| `GET` | `/api/games/{id}/state` | Current redacted `GameView` |
| `GET` | `/api/games/{id}/decision` | The pending decision, if any |
| `GET` | `/api/games/{id}/events` | SSE stream of `SessionEvent` (hand-implemented — see `puerto-rico-contract`'s README) |
| `POST` | `/api/games/{id}/moves` | Offer a move for a human seat |
| `GET` | `/api/ai/engines` | AI engines available to seat |

- Consumes the **Lobby contract** exposed by `puerto-rico-lobby`.
- Consumes the **Event/broadcast contract** produced by `puerto-rico-session`,
  via `GameEventStream` bridging `SessionListener` to `SseEmitter`.
- Implements the **Decision contract** (via `HumanActor`) defined by
  `puerto-rico-session`, and calls into `puerto-rico-ai`'s `AiRegistry` to
  seat AI opponents.
- Speaks the wire types generated by `puerto-rico-contract` — never a
  hand-written DTO.

## Depends on

`puerto-rico-lobby`, `puerto-rico-ai`, `puerto-rico-contract`,
`puerto-rico-frontend`, and transitively `puerto-rico-session` and
`puerto-rico-model`.

## Design notes

**A seat token is what authorizes acting as that seat.** `SeatTokens`
mints an opaque token when a human seats, returned once in the seat
response; `POST /moves` requires it via `X-Seat-Token`, matched against the
move's own `action.seat`. This is the smallest thing that answers
architecture.md's open "player/spectator permission boundary" question:
everyone can read every endpoint, only a token holder can post a move for
that seat.

**`POST /moves` returns 202, not the post-move state.** `HumanActor.offer`
only completes that seat's pending future — the actual `GameSession.submit`
call happens later, on `SessionRunner`'s own thread, not the HTTP request
thread. There is no synchronous "did it apply" to report. The event stream
is the source of truth for when a move actually lands; this endpoint only
confirms the offer was accepted for consideration.

**`HumanActor.offer` validates before completing the future**, and is the
only path a human move may take to reach the game — never straight to
`GameSession.submit`. Two reasons: `SessionRunner` aborts a game after
three consecutive unusable answers, so an unvalidated illegal move would
burn that budget on a stale click rather than refusing it outright; and
submitting directly would advance the game while the runner still holds
this actor's unresolved future, leaving it waiting forever on a decision
already answered a different way.

**Rejection stays a value through the mapping layer too.**
`ApiException` carries an HTTP status, a title, and — when the failure
traces back to one — a `RejectionReason` or `LobbyRejectionReason` enum
name, surfaced as `Problem.reason` in the response body. Controllers throw
it; `ApiExceptionHandler` is the one place it becomes an HTTP response.

**`GameEventStream`'s fan-out never blocks the game on a slow client.** A
`SessionListener` runs on the session's own thread; an emitter that throws
(closed connection, write failure) is dropped from that game's subscriber
list rather than allowed to wedge the others.

## Testing

JUnit 5 (not TestNG) — `@SpringBootTest` + MockMvc are Spring Boot's own
idiomatic testing tools, already inherited via `spring-boot-starter-test`,
and forcing TestNG onto Spring's test slices would fight the framework for
no benefit. AssertJ throughout, matching every other module.

| Test class | Covers |
|---|---|
| `WireMappingTest` | Every mapper (`ActionMapper`, `GameMapper`, `SessionEventMapper`, `LobbyMapper`) is total and correct — the seam the generator can't check for us |
| `HumanActorTest` | `decide`/`offer` state machine: incomplete future, valid completion, stale requestId, illegal action, no pending decision, double-offer — all rejected without ever completing the future incorrectly |
| `LobbyApiTest` | `@SpringBootTest` + MockMvc: create/list/seat/start happy paths; every `LobbyRejectionReason` maps to its status and body |
| `GameApiTest` | `/state`, `/decision`, `/moves` — including the seat-token checks and a full seat-to-move round trip against a real started game |
| `GameEventStreamTest` | Fan-out to zero subscribers and to a completed (dead) emitter, both without propagating |

```bash
./mvnw -pl puerto-rico-web -am verify
./mvnw -pl puerto-rico-web spring-boot:run   # http://localhost:8080
```
